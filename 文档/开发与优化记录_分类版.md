1.问题分类 
环境配置类 — Windows PowerShell 脚本执行安全策略
2.现象描述 
我在VS Code里面准备开启Python虚拟环境，输入激活命令之后直接弹出权限报错，系统不让运行这条脚本，虚拟环境启动不了，项目没法跑起来。
3.排查过程与解决方案 
原因排查：PowerShell自带一套安全限制，默认不允许运行本地写好的脚本，激活虚拟环境的脚本刚好被这条规则拦住了。
解决方案（二选一）
方案A：用管理员身份打开PowerShell，输入 `SetExecutionPolicy RemoteSigned -Scope CurrentUser`，输入`Y`确认，放宽安全限制。
方案B：换一个终端，把PowerShell切换成CMD，用CMD里面对应的命令去开启虚拟环境。 
4.经验总结 
这是新手使用虚拟环境很容易碰到的问题。经过这次问题，我搞懂了这个安全限制，以后遇到同类问题可以快速解决。

1.问题分类 
安全与配置管理类 — API密钥存放路径与代码安全冲突 
2.现象描述 
连接大模型的时候需要填写密钥。我把存放密钥的`.env`文件放在项目根文件夹程序就读取不到，如果放到源代码文件夹里面，如果上传代码到网上，密钥就会泄露出去，存在安全风险。
3.排查过程与解决方案 
原因排查：程序读取密钥文件，是根据打开终端时所在的文件夹去找文件的，如果位置不对就找不到。代码文件夹的文件会被同步上传，密钥放在这里很危险。
解决方案：把`.env`密钥文件固定放在项目最外层文件夹，同时在根目录下新建gitinore，设置规则不让.env跟着代码一起上传。运行代码的时候，确保终端打开的是项目根目录，再启动程序。
4.经验总结 
不能直接把密码、密钥写在代码里面。这次调整找到了兼顾方便和安全的存放方式，懂得了保护项目里面重要私密信息。

记录编号：DEV-012
1. 问题分类
相对路径读取异常导致配置加载失败
2. 现象描述
程序在终端环境可正常运行，在网页服务环境启动后，出现服务器连接失败问题，核心原因为环境配置读取失效。
3. 排查过程与解决方案
问题原因：终端与网页端的启动目录不同，相对路径读取规则不稳定。网页端无法正确定位配置文件，导致关键参数缺失。
解决方式：取消默认相对路径读取方式，统一使用绝对路径定位配置文件，不受程序启动目录影响，保证多运行环境配置统一加载。
4. 经验总结
多入口、多场景运行的项目，必须采用固定绝对路径加载配置资源，规避路径切换带来的未知报错。

跨设备远程通信需要匹配对应的网络模式，根据业务场景合理选择网络架构，是保障连通性的基础。

1. 问题分类
隐性网络故障缺乏标准化排查流程
2. 现象描述
虚拟机IP地址更新后，系统依旧提示连接超时，程序无明确报错信息，问题排查效率较低。
3. 排查过程与解决方案

4. 经验总结
针对无明确报错的隐性故障，需要建立层级化、标准化的排查流程，缩小问题范围，避免盲目调试。
分类二：AI 行为、Prompt 与边界控制
记录编号：DEV004 
1.问题分类
Agent工具设计类 — Linux命令悄悄失败，AI误以为任务做完 
2.现象描述
让AI去操作Linux服务器的时候出现奇怪情况。举个例子：让它重启网站服务，屏幕上面看不出任何报错，但实际上服务并没有成功启动，AI以为任务已经顺利完成，继续往下执行操作，导致后续全部出错。
3.排查过程与解决方案
原因排查：程序只会根据报错文字进行反应，有些Linux命令失败的时候不会打出提示文字，AI会误以为本行代码没有问题，后续因为这个原因报错的话AI只会检查报错的那一行代码，不会联想到是前面的代码有错误。
解决方案：修改工具代码，除了读取屏幕文字，同时读取代表执行结果的数字。把成功或者失败的状态明确告诉AI，让它可以分辨任务到底有没有做完。
4.经验总结 
让AI操作电脑不能只看屏幕文字。加上执行状态判断之后，AI不容易产生误判，整套智能程序运行起来更加稳定。
记录编号：DEV-005
1. 问题分类
AI 边界情况与异常输入处理（垃圾数据、乱码、日常聊天、Prompt注入）
2. 现象描述
目前尚未进行专项测试。预计当用户输入“今天中午吃什么”等非运维相关的日常对话时，大模型可能会受限于固定格式的 Prompt，强行生成不符合逻辑的假报错诊断，产生“格式幻觉”。
3. 排查过程与解决方案
测试表现：AI 表现良好，能够成功识别出“不是有效的运维日志”。它没有强行生成错误诊断格式，而是礼貌地提示用户“请粘贴相关的错误日志”。成功避免了大模型的“格式幻觉”。
加固措施（双保险预案）：虽然 AI 层面表现良好，但为了未来的稳定性，规划了后续加固方案：
  1. Prompt 防护栏：在 `SYSTEM_PROMPT` 中正式加入“如果输入与 Linux 运维无关，请拒绝分析并引导用户重新输入”的强制指令。
  2. 代码层前置拦截：计划在 `main.py` 中增加轻量级的关键词/长度过滤，避免无效的 API 调用，降低 token 消耗。
4. 经验总结
深刻理解了“边界测试”对 AI 应用的重要性。AI 不是万能的，但通过良好的 Prompt 设计，可以极大地增强其鲁棒性（Robustness）。在开发中，不能只测试“正确流程”，更要测试“异常流程”，这样才能构建出值得用户信赖的工具。

解决方式：调整代码判断顺序，将高危致命操作拦截设置为最高优先级，命中后直接强制拒绝，不提供人工确认入口。同时优化正则匹配规则，去除空格干扰，提升拦截准确率。
4. 经验总结
系统安全红线必须具备最高执行优先级，高危致命操作不允许人工确认，从机制上杜绝系统损毁风险。

记录编号：DEV-013
1. 问题分类
网页端线程阻塞导致页面卡死
2. 现象描述

3. 排查过程与解决方案
问题原因：终端式同步等待输入逻辑会阻塞网页主线程，不符合网页异步交互机制。
解决方式：重构确认交互架构，将终端确认迁移至网页前端。需要人工确认时，后端返回标记信息，前端渲染操作按钮，由用户网页端交互完成授权，避免线程阻塞。
4. 经验总结
网页服务不支持阻塞式等待操作，所有人机交互流程必须适配异步架构，保证页面稳定可用。
